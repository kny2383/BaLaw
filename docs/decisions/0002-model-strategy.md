# 0002. 모델 교체 가능 구조와 공급자 비교

- 상태: **확정** (2026-11-25)
- 관련: `metrics.md`, 결정 0001

## 배경

- AI 모델은 계속 새로 나온다. 모델이나 공급자가 바뀔 때마다 서비스 코드를 고치지 않도록 구조를 정해 둔다.
  - 필요한 것은 공급자를 설정으로 바꾸는 구조, 기준 날짜가 붙은 가격표, 같은 평가 세트로 하는 비교다.
- 바로의 AI 코드는 OpenAI SDK에 직접 묶여 있다 (2026-11-25 기준).

| 위치 | 하는 일 | 문제 |
|---|---|---|
| `ai/services/openai_client.py` | 필수 정보 추출, 고소장 작성 호출 | 실패 시 빈 문자열 반환 (M10) |
| `ai/services/rag.py` | 판례 키워드 예측, 판례 요약 호출, 임베딩 | 별도 OpenAI 클라이언트를 따로 만듦 |
| `ai/services/rag_bootstrap.py` | 판례 벡터 DB 생성 시 임베딩 | OpenAI 임베딩에 고정 |
| `ai/cfg.py` | 모델 이름 | 작성 모델과 대화 모델이 같은 환경 변수 `OPENAI_MODEL`을 읽어 따로 지정할 수 없음 |

## 결정

### 1. 모든 LLM 호출을 한 계층으로 모은다 (4단계, 구조 변경)

- 앱 코드는 "작업 이름, 메시지, 출력 형식"만 넘기고, 어떤 공급자·모델을 쓸지는 설정이 정한다.
- 공급자 어댑터: OpenAI, Anthropic, Google, 오픈소스(OpenAI 호환 API를 내는 로컬 서버, 예: Ollama).
- 작업별 모델 설정: 판례 키워드, 판례 요약, 필수 정보 추출, 질문, 고소장 작성, 평가 판정.
- 모든 호출은 같은 형식으로 기록한다: 작업, 공급자, 모델 판본, 입력·출력·추론 토큰, 비용, 지연, 성공·실패.
- 실패는 빈 값으로 바꾸지 않고 오류로 올린다.
- 이 단계에서는 모델을 바꾸지 않는다. 같은 모델을 새 계층으로 불러 평가기 숫자가 기준선과 같은지 확인한다.
- 외부 통합 라이브러리(예: LiteLLM)를 쓸지는 구현 시점에 비교해 결정 기록을 따로 남긴다. 직접 만드는 얇은 계층이 기본안이다.

### 2. 같은 평가 세트로 공급자를 작업별로 비교한다 (5단계, 동작 변경)

| 작업 | 보는 지표 | 확인할 가설 |
|---|---|---|
| 필수 정보 추출 | M2, M11, 구조화 출력 실패율 | 추론형 모델이 꼭 필요한가 |
| 고소장 작성 | M1, M8, IRAC(참고) | 한국어 법률 문체는 어느 모델이 안정적인가 |
| 평가 판정 | 사람 판정과의 일치율 | 판정 모델은 서비스 모델과 다른 회사 것을 써야 하는가 |
| 개인정보가 많은 단계 | M9, 품질 | 로컬 오픈소스로 외부 전송을 없앨 수 있는가 |

- 비교는 개발 세트로만 돌리고, 최종 선택만 보류 세트로 확인한다.
- 결과는 작업별 모델 선택 결정 기록으로 남긴다.

### 3. 새 모델이 나왔을 때의 절차

1. 설정에 후보 모델을 추가한다 (코드 변경 없음).
2. 평가기로 현재 모델의 기준선과 비교한다.
3. 품질·비용·지연 기준을 넘으면 결정 기록을 남기고 설정을 바꾼다.
4. 문제가 생기면 설정을 되돌린다.

모델은 날짜가 붙은 판본으로 고정하고, 가격표에는 기준 날짜를 둔다.

## 범위 밖

- **임베딩 모델 교체.** 판례 벡터 DB 11,393건을 다시 만들어야 해서 생성 모델 비교와 분리한다. 하게 되면 임베딩 후보를 같은 질의 세트로 비교해 따로 결정한다.

## 평가기에 주는 요구사항 (2단계)

- 판정 모델을 설정으로 고를 수 있어야 한다.
- 비용은 기준 날짜가 붙은 가격표로 계산한다.
- 호출 기록 형식은 위 1번의 형식과 맞춰, 4단계 이후에도 평가기를 바꾸지 않고 쓸 수 있게 한다.
