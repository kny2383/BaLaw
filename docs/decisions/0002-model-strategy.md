# 0002. 모델 교체 가능 구조와 공급자 비교

- 상태: **확정** (2026-11-25)
- 관련: `metrics.md`, 결정 0001

## 배경

- AI 모델은 계속 새로 나온다. 모델이나 공급자가 바뀔 때마다 서비스 코드를 고치지 않도록 구조를 정해 둔다.
  - 필요한 것은 공급자를 설정으로 바꾸는 구조, 기준 날짜가 붙은 가격표, 같은 평가 세트로 하는 비교다.
- 바로의 AI 코드는 OpenAI SDK에 직접 묶여 있다 (2026-11-25 기준).

| 위치 | 하는 일 | 문제 |
|---|---|---|
| `ai/services/openai_client.py` | 필수 정보 추출, 고소장 작성 호출 | 실패 시 빈 문자열 반환 (M10) |
| `ai/services/rag.py` | 판례 키워드 예측, 판례 요약 호출, 임베딩 | 별도 OpenAI 클라이언트를 따로 만듦 |
| `ai/services/rag_bootstrap.py` | 판례 벡터 DB 생성 시 임베딩 | OpenAI 임베딩에 고정 |
| `ai/cfg.py` | 모델 이름 | 작성 모델과 대화 모델이 같은 환경 변수 `OPENAI_MODEL`을 읽어 따로 지정할 수 없음 |

## 결정

### 1. 모든 LLM 호출을 한 계층으로 모은다 (4단계, 구조 변경)

- 앱 코드는 "작업 이름, 메시지, 출력 형식"만 넘기고, 어떤 공급자·모델을 쓸지는 설정이 정한다.
- 공급자 어댑터: OpenAI, Anthropic, Google, 오픈소스(OpenAI 호환 API를 내는 로컬 서버, 예: Ollama).
- 작업별 모델 설정: 판례 키워드, 판례 요약, 필수 정보 추출, 질문, 고소장 작성, 평가 판정.
- 모든 호출은 같은 형식으로 기록한다: 작업, 공급자, 모델 판본, 입력·출력·추론 토큰, 비용, 지연, 성공·실패.
- 실패는 빈 값으로 바꾸지 않고 오류로 올린다.
- 이 단계에서는 모델을 바꾸지 않는다. 같은 모델을 새 계층으로 불러 평가기 숫자가 기준선과 같은지 확인한다.
- 외부 통합 라이브러리(예: LiteLLM)를 쓸지는 구현 시점에 비교해 결정 기록을 따로 남긴다. 직접 만드는 얇은 계층이 기본안이다.

**구현 (2026-11-27)**: `ai/services/llm.py`.

- 서비스 코드는 `llm.text("compose", ...)`, `llm.parsed("extract", ..., 스키마)`처럼 작업 이름으로 부른다. 작업은 여섯 가지다: 정보 추출, 초안 작성, 초안 검증, 재작성, 죄명 키워드, 판례 요약.
- 작업별 모델은 `LLM_MODEL_<작업>`, 작업별 주소는 `LLM_BASE_URL_<작업>`으로 바꾼다. 지정하지 않으면 이전과 같은 모델을 쓴다.
- **주소를 지정한 작업에는 OpenAI 키를 보내지 않는다.** 그 서버의 키는 `LLM_API_KEY_<작업>`으로 따로 준다. 처음 구현은 어느 주소로든 OpenAI 키를 실어 보냈고, 리뷰에서 지적받아 고쳤다. 주소를 바꾸면 사용자 서술이 담긴 요청이 그 서버로 간다는 점은 그대로이므로, 믿을 수 있는 서버에만 쓴다.
- 모델 객체는 LangChain의 채팅 모델 인터페이스다 (결정 0003). 직접 어댑터를 만들지 않았다.
- **연결된 공급자는 OpenAI와 OpenAI 호환 서버뿐이다.** Anthropic, Google은 붙이지 않았다. 붙이려면 공급자 패키지를 더하고 `_PROVIDERS`에 모델을 만드는 함수를 하나 넣는다. 구조화 출력의 요청 형식이 공급자마다 달라 그 부분도 함께 손봐야 한다.
- 호출 기록: 작업, 공급자, 모델, 프롬프트 판본, 입력·캐시된 입력·출력·추론 토큰, 비용, 걸린 시간, 성공 여부를 호출마다 한 줄로 남긴다. 프롬프트와 응답 내용은 남기지 않는다.
  - 비용은 `ai/prices.json`의 단가로 계산한다. 평가기도 같은 파일을 읽는다. 계산할 수 없으면(실패한 호출, 단가표에 없는 모델, 주소를 바꾼 작업) 0이 아니라 빈 값으로 둔다.
  - 프롬프트 판본은 죄목별 기준 요청(`ai/tests/fixtures/llm_requests*.json`, 사기와 모욕)의 메시지와 출력 형식을 함께 해시한 값이다. 어느 죄목의 문구를 바꿔도 판본이 바뀐다. 기준 사례의 서술도 요청에 들어가므로, 그 서술을 고치면 프롬프트가 그대로여도 판본이 바뀐다. 판본이 바뀐 시점은 `ai/prompt_versions.json`의 변경 이력에서 무엇이 바뀌었는지와 함께 본다. 프롬프트를 바꾸면 기준 요청과 판본(`ai/prompt_versions.json`)을 함께 다시 만든다.
  - 세션 표지는 세션 값을 해시한 12자다. 한 고소장의 호출(대화, 작성, 검증, 재작성, 판례 검색)을 묶어 보는 데 쓴다. 세션 값 자체는 그 세션의 대화를 읽을 수 있는 값이라 기록과 실패 로그에 남기지 않는다.
- 호출 기록 집계: 작업별 호출 수, 실패 수와 이유, 걸린 시간 p50·p95, 토큰, 비용을 낸다. 실행 중인 서비스는 `GET /llm/stats`(최근 5,000건, 재시작하면 빈다. 기본은 닫혀 있고 `LLM_STATS_TOKEN`을 설정해 `Authorization: Bearer`로 불러야 열린다), 로그에 남은 기록은 `docker compose logs ai | python -m services.llm_stats`로 본다. 비용을 계산하지 못한 호출 수를 함께 내서 합계가 작게 나온 것을 알 수 있게 한다. 세션 단위로는 세션 수, 세션당 호출 수, 세션당 비용(평균·p50·p95)을 낸다. 비용을 모르는 호출이 섞인 세션은 비용 통계에서 빼고 수만 센다.
- **같다는 확인**: 바꾸기 전 코드가 보내는 요청 본문을 호출 종류별로 저장해 두고(`ai/tests/fixtures/llm_requests.json`), 지금 코드의 요청과 비교하는 테스트를 둔다. 차이는 하나다. 글로 받는 요청에 `stream: false`가 명시된다 (뜻은 같다). 평가기를 다시 돌리는 대신 이 방법을 썼다.
- **달라진 동작 하나**: 죄명 키워드 호출이 빈 글을 돌려주면 예전에는 빈 키워드로 거르지 않은 판례를 보여 줬다. 지금은 오류로 올라가 판례 검색이 실패로 남고, 대화는 이어진다. 구조 변경(#49)에 함께 들어갔고 테스트는 뒤에 더했다.
- 임베딩 호출은 옮기지 않았다 (범위 밖).

### 2. 같은 평가 세트로 공급자를 작업별로 비교한다 (5단계, 동작 변경)

| 작업 | 보는 지표 | 확인할 가설 |
|---|---|---|
| 필수 정보 추출 | M2, M11, 구조화 출력 실패율 | 추론형 모델이 꼭 필요한가 |
| 고소장 작성 | M1, M8, IRAC(참고) | 한국어 법률 문체는 어느 모델이 안정적인가 |
| 평가 판정 | 사람 판정과의 일치율 | 판정 모델은 서비스 모델과 다른 회사 것을 써야 하는가 |
| 개인정보가 많은 단계 | M9, 품질 | 로컬 오픈소스로 외부 전송을 없앨 수 있는가 |

- 비교는 개발 세트로만 돌리고, 최종 선택만 보류 세트로 확인한다.
- 결과는 작업별 모델 선택 결정 기록으로 남긴다.

### 3. 새 모델이 나왔을 때의 절차

1. 설정에 후보 모델을 추가한다 (코드 변경 없음).
2. 평가기로 현재 모델의 기준선과 비교한다.
3. 품질·비용·지연 기준을 넘으면 결정 기록을 남기고 설정을 바꾼다.
4. 문제가 생기면 설정을 되돌린다.

모델은 날짜가 붙은 판본으로 고정하고, 가격표에는 기준 날짜를 둔다.

### 4. 모델 이전 (2026-11-27 추가)

위 절차를 처음 쓰는 경우다. 새 모델이 나와서가 아니라 쓰던 모델이 종료돼서 옮긴다.

**확인한 사실** (OpenAI 문서, 2026-11-27):

| 지금 쓰는 모델 | 쓰는 곳 | 종료 | 문서가 적은 대체 모델 |
|---|---|---|---|
| `gpt-5-mini` | 서비스의 호출 여섯 종류 모두 | 2026-12-11 | `gpt-6.1-terra` |
| `gpt-5` | 평가 판정 | 2026-12-11 | `gpt-6.1-sol` |
| `text-embedding-3-small` | 판례 검색 | 종료 목록에 없음 | - |

별칭과 날짜가 붙은 판본이 같은 날 종료된다. 종료 뒤 별칭이 다른 모델로 넘어가는지는 문서에 없다.

**후보와 단가** (100만 토큰당 달러, 입력 / 캐시된 입력 / 출력, 입력 272K 이하):

| 모델 | 단가 | 지금 대비 |
|---|---|---|
| `gpt-5-mini` (지금) | 0.25 / 0.025 / 2.00 | - |
| `gpt-6-luna` | 0.10 / 0.01 / 0.50 | 입력 0.4배, 출력 0.25배 |
| `gpt-6.1-terra` | 1.00 / 0.05 / 5.00 | 입력 4배, 출력 2.5배 |
| `gpt-6.1-sol` | 2.00 / 0.10 / 10.00 | 입력 8배, 출력 5배 |

네 모델의 단가는 모두 가격 문서에서 직접 확인했다 (2026-11-27). `gpt-6-sol`은 캐시 단가가 다른 별개 모델이다 (0.20).

`gpt-6-luna`와 `gpt-6.1-terra`는 지금 쓰는 호출 방식(chat completions)과 구조화 출력을 지원한다고 모델 설명 문서에 적혀 있다. `gpt-6.1-sol`도 같다. 다만 이 모델은 추론 강도에 `none`이 없다 (`low`부터). `gpt-6-luna`와 `gpt-6.1-terra`는 정보 추출 호출로 실제 동작을 확인했다 (구조화 출력 실패 0건, `eval/results/extract-model-dev10.md`). `gpt-6.1-sol`은 판정 호출로 확인했다 (10건 × 2회, 실패 0건, `eval/results/judge-model-dev10.md`).

**정하는 방식**: 작업마다 따로 정한다. 호출 수와 요구가 다르기 때문이다.

- 정보 추출: 호출이 가장 많고 응답 대기 시간의 대부분이다. 싼 모델(`gpt-6-luna`)로 충분한지부터 본다. 정답과 비교하는 지표(M2)라 판정 모델 없이 잰다.
- 작성·검증·재작성: 호출이 고소장 한 건에 한두 번이다. 단가가 높은 모델을 써도 건당 비용 부담이 작으므로 품질(M1)을 먼저 본다.
- 판정: 서비스 모델을 바꾸기 전에 판정 모델부터 정한다. 같은 초안을 옛 판정과 새 판정으로 판정해 차이를 적어 두어야, 서비스 모델을 바꾼 뒤의 숫자를 이전 숫자와 이을 수 있다.

**정한 것** (정해지는 대로 더한다):

- 판정 모델: `gpt-6.1-sol` (2026-11-27). 근거는 `eval/results/judge-model-dev10.md`.
- 초안 작성·검증·재작성: `gpt-6.1-terra` (2026-11-27). 근거는 `eval/results/service-model-dev10.md`. 설정의 기본값은 정보 추출 모델을 정한 뒤 함께 바꾼다.

**달라지는 것**:

- 위의 "날짜가 붙은 판본으로 고정"은 새 모델에서 할 수 없다. 문서에 날짜가 붙은 판본이 없고 별칭만 있다. 결과 문서에는 응답에 적힌 모델 이름과 실행 날짜를 남긴다.
- 지금까지의 측정 결과는 종료되는 모델의 것이다. 옮긴 뒤 개발 세트의 기준을 다시 잰다.

## 범위 밖

- **임베딩 모델 교체.** 판례 벡터 DB 11,393건을 다시 만들어야 해서 생성 모델 비교와 분리한다. 하게 되면 임베딩 후보를 같은 질의 세트로 비교해 따로 결정한다.

## 평가기에 주는 요구사항 (2단계)

- 판정 모델을 설정으로 고를 수 있어야 한다.
- 비용은 기준 날짜가 붙은 가격표로 계산한다.
- 호출 기록 형식은 위 1번의 형식과 맞춰, 4단계 이후에도 평가기를 바꾸지 않고 쓸 수 있게 한다.
