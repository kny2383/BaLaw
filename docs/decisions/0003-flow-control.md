# 0003. 대화 흐름 제어 방식: 직접 구현 대 LangGraph

- 상태: **확정** (2026-11-26)
- 관련: 결정 0002, `roadmap.md` 4·5단계, 지표 M1·M5·M10·M11

## 배경

- 지금 대화 흐름은 "정보 추출(LLM) → 규칙으로 다음 질문 선택"의 반복이고, 끝나면 초안을 작성한다 (`ai/baroai.py`의 `_send_to_session`).
- 세션 상태는 메모리의 딕셔너리다. 서버가 재시작하면 사라지고, 복원할 때 지난 사용자 답을 LLM에 다시 돌린다 (`/chat/restore`).
- 앞으로 넣을 기능은 흐름이 멈추거나 갈라진다.

| 넣을 기능 | 흐름의 모양 | 관련 지표 |
|---|---|---|
| 작성 전 사용자 확인 | 멈췄다가 이어 감 | M1 |
| 초안 검증 후 재작성 | 조건에 따라 되돌아감 | M1 |
| 추출 실패 시 재시도 후 오류 | 조건에 따라 되돌아감 | M10 |
| 미지원 죄목, 죄목별 경로 | 갈라짐 | M5 |

## 검토한 선택지

| | 직접 구현 (상태 기계) | LangGraph |
|---|---|---|
| 구현량 | 가장 적다. 상태 값과 조건문, 반복문 | 그래프 정의와 상태 스키마가 추가된다 |
| 상태 저장 | 딕셔너리를 JSON으로 DB에 저장 | PostgreSQL 체크포인트 지원 |
| 멈췄다 이어 가기 | 상태에 "확인 대기" 값을 두고 다음 요청에서 처리 | interrupt |
| 단계별 추적 | 직접 로그를 남겨야 한다 | 단계별 입력·출력이 기록된다 |
| 병렬 실행 | 지금처럼 백그라운드 작업 | 한 그래프 안에서 병렬 |
| 의존성 | 없음 | LangGraph와 LangChain 코어 |
| 위험 | 흐름이 커지면 조건문이 얽힌다 | 버전에 따라 API가 바뀐다. 체크포인트에 대화가 평문으로 남는다 |

검토했지만 고르지 않은 것:

- **도구 호출형 에이전트**: LLM이 다음 행동을 스스로 고른다. 바로는 순서가 정해진 흐름이고, 법률 문서에서는 예측 가능성이 더 중요하다.
- **장기 실행 워크플로 엔진**: 며칠짜리 작업을 위한 도구라 이 규모에는 과하다.

## 결정

LangGraph로 구현한다.

- **인정하는 사실**: 지금 규모에서는 직접 구현이 더 단순하다. 세션 저장만이 목적이라면 LangGraph는 필요 없다.
- **고른 이유**
  1. 넣을 기능 네 가지가 모두 멈추거나 갈라지는 흐름이라, 흐름을 조건문이 아닌 구조로 드러내는 편이 낫다.
  2. 단계별 추적으로 지어낸 사실이 어느 단계에서 들어오는지 좁힐 수 있다.

## 진행 순서

1. **이식 (구조 변경)**: 현재 흐름을 그대로 그래프로 옮긴다 (추출 → 질문 선택 → 작성). 분류 단계나 사용자 확인 단계는 지금 코드에 없으므로 이때 넣지 않는다. 평가기로 이식 전과 같은 범위의 숫자가 나오는지 확인한다.
2. **기능 추가 (동작 변경)**: 사용자 확인, 검증 후 재작성을 각각 따로 넣고 M1 전후를 잰다.

정보 추출 호출 개선은 이식보다 먼저 한다. 서비스 비용의 90%가 이 호출이라, 먼저 고쳐야 이식의 동일성 확인 비용이 줄어든다 (`roadmap.md` 진행 순서).

## 이식 설계 (2026-11-26)

- **요청 하나가 그래프 실행 한 번이다.** 요청이 오면 체크포인터에서 세션 상태를 불러와 한 번 실행하고 끝낸다. 그래프가 멈춰서 사용자의 다음 발화를 기다리는 방식(interrupt)은 쓰지 않는다. 발화마다 멈추는 방식은 실패한 턴을 되돌리는 처리가 따로 필요하고, 작성 요청도 같은 대기 지점에서 받아야 해 구조가 어색하다. interrupt는 실행 도중에 사람의 확인이 필요한 "작성 전 사용자 확인"에서 쓴다.
- **대화 그래프** (`ai/flow/chat_graph.py`): 요청 종류로 갈라진다. `init`은 처음 상태를 만들고, `message`는 `extract → select_question`, `compose`는 `compose`를 실행한다.
- **판례 그래프** (`ai/flow/rag_graph.py`): `predict_keyword → search_cases → summarize_cases`. 초기화 때 백그라운드로 실행되어 첫 대화 턴과 겹치므로 같은 세션의 별도 thread에 저장한다. 한 thread에 두 실행이 동시에 쓰면 나중에 끝난 쪽이 앞의 결과를 덮어쓴다.
- **추출 노드는 성공했을 때만 발화를 기록에 넣는다.** 실패하면 그 노드의 결과가 저장되지 않으므로, 다시 보내면 같은 상태에서 이어진다.
- **순서**: 먼저 메모리 체크포인터로 흐름만 옮기고(API와 동작은 그대로), 다음에 PostgreSQL 체크포인터와 암호화, 세션 삭제를 넣는다. 대화가 DB에 남기 시작하는 시점에 암호화와 삭제가 함께 들어가야 한다.

### 체크포인트 저장과 암호화

- **저장소**: `CHECKPOINT_DB_URL`이 있으면 PostgreSQL의 `ai_checkpoint` 스키마에 저장한다. 서버의 테이블과 섞이지 않게 스키마를 나눴다. 주소가 있는데 암호화 키(`CHECKPOINT_AES_KEY`)가 없으면 서비스가 뜨지 않는다.
- **암호화가 닿지 않는 값이 있다.** LangGraph의 암호화 직렬화기는 dict·list 값만 암호화한다. 문자열·숫자·불리언 값은 암호화 없이 JSON 열에 그대로 들어간다. 처음 옮긴 상태로 실제 DB를 훑어 보니 질문 문장, 판례 검색에 쓴 사건 서술, 죄명 키워드가 평문으로 남아 있었다.
- **대응**: 대화에서 나온 글은 모두 dict나 list 안에 둔다 (`ai/flow/state.py`). 최상위에 단순 값으로 두는 것은 죄목 양식 코드와 "죄목을 직접 골랐는가" 표시뿐이다. 실제 PostgreSQL에 대화를 저장한 뒤 모든 테이블의 모든 열에서 사용자 발화와 LLM이 만든 글을 찾아보는 테스트가 이 규칙을 지킨다. 같은 검사가 암호화를 뺀 저장소에서는 글을 찾아내는지도 함께 확인한다.
- **지난 단계 사본**: 그래프는 단계마다 상태 사본을 저장한다. 같은 대화가 여러 벌 쌓이지 않게 요청이 끝날 때마다 최신 상태 하나만 남긴다. 단계별 기록이 필요한 분석(가상 사례로 지어낸 사실이 들어오는 단계 찾기)에서는 `CHECKPOINT_KEEP_HISTORY=1`로 남긴다.
- **삭제**: `DELETE /chat/{session_id}`가 세션의 대화와 판례 검색 상태를 모두 지운다.
- **키를 잃거나 바꾸면** 저장된 세션은 읽을 수 없다. 키 교체 절차는 아직 없다.

### 검증 후 재작성 (2026-11-26)

- **흐름**: `compose → verify → rewrite`. 검증은 대화 기록(질문과 답)과 초안을 대조해 근거 없는 표현을 찾고, 재작성은 그 표현만 고쳐 다시 쓴다. 근거 없는 표현이 없으면 재작성하지 않는다.
- **반복 상한**: `DRAFT_MAX_REWRITES`(기본 1). 상한까지 고쳤으면 다시 검증하지 않고 끝낸다. 검증 호출 한 번이 응답 시간과 비용에 그대로 더해지기 때문이다. 0이면 검증을 끄고 이전 동작과 같다.
- **확인 대상이 초안인 이유**: 지어낸 사실의 73%가 작성 단계에서 생긴다 (`eval/results/m1-origin-dev10.md`).
- **실패 처리**: 검증 호출이 실패하면 초안은 그대로 두고 `unverified`로, 재작성 결과를 쓸 수 없으면 `rewrite_failed`로 응답에 남긴다. 검증된 초안처럼 돌려주지 않는다.
- **응답**: `/chat/compose` 응답에 `verification`(`status`, `rewrites`, `rechecked`, `unsupported`, `removed`)이 붙는다. 기본 상한에서는 고쳐 쓴 초안을 다시 검증하지 않으므로 `rewritten`이어도 `rechecked`는 false다. 고쳐 쓴 초안이 검증을 통과했다는 뜻이 아니다. 사용자 확인 단계는 이 목록을 사용자에게 보여 주는 데서 시작한다.
- **치르는 비용**: 작성 요청마다 LLM 호출이 1~2회 늘어난다. 검증과 재작성 호출에는 식별정보를 표식으로 바꾼 대화와 초안이 들어간다 (S05). 치환이 닿지 않는 값(입력 화면에 없는 이름 등)은 추출 호출과 마찬가지로 그대로 나간다.

### 사용자 확인 (2026-11-26)

- **흐름**: `DRAFT_CONFIRM=1`이면 `verify`와 `rewrite` 사이에 `confirm`이 들어간다. `confirm`은 `interrupt`로 실행을 멈추고, `/chat/compose` 응답은 `verification.status`가 `awaiting_confirmation`이며 물을 표현이 `to_confirm`에 담긴다. `/chat/compose/confirm`에 표현마다 참/거짓으로 답하면 멈춘 자리에서 이어서, 사실이 아니라고 한 표현만 고쳐 쓴다.
- **묻는 이유**: 검증이 찾은 표현 가운데 일부는 사용자가 실제로 겪었지만 대화에서 말하지 않은 사실이다. 자동으로 고치면 그 내용이 빠지거나 문서가 약해진다 (`eval/results/prompt-verify-dev10.md`). 사실인지는 사용자만 안다.
- **사실이라고 답한 표현**: 초안에 남기고, 그 답을 사용자 발화로 대화 기록에 더한다. 다시 검증할 때 근거가 된다.
- **묻는 범위**: 검증은 문장 전체가 아니라 근거 없는 구절만 인용한다. 구절이 든 문장은 코드가 초안에서 찾아 `sentence`로 함께 돌려주고, 화면은 문장 안에서 구절을 강조한다. 문장 전체를 보여 주면 무엇을 묻는지 알기 어려웠다 (`eval/results/confirm-phrase-dev10.md`: 문장 전체 인용 50% → 29%).
- **묻는 개수**: 한 번에 `DRAFT_CONFIRM_MAX`(기본 5)개까지 묻는다. 넘는 것은 묻지 않고 고친다.
- **기다리는 동안**: 멈춘 상태는 체크포인터에 남는다. 지난 단계를 정리하거나 서비스가 재시작해도 답을 받으면 이어 간다. 답 대신 새 발화나 작성 요청이 오면 기다리던 확인은 버리고 새로 실행한다.
- **멈출 때 넘기는 값**: 개수만 넣는다. 물을 표현은 암호화되어 저장되는 상태(`review`)에서 읽는다.
- **형식이 틀린 답**: 받지 않고 다시 멈춘다. 노드에서 예외를 내면 틀린 답이 저장된 채 남아 다음 답을 가리기 때문이다.
- **기본은 꺼짐**: 서버와 화면이 `awaiting_confirmation`을 다루기 전까지는 묻지 않고 고치는 이전 동작을 유지한다.

## 결정 0002와의 관계

결정 0002의 "모든 LLM 호출을 한 계층으로 모은다"는 그대로다. 다만 공급자 교체는 직접 어댑터를 만들지 않고 LangChain의 모델 인터페이스를 쓴다. 바로의 호출 계층은 그 위에 작업별 모델 설정과 호출 기록만 더한다.

## 치르는 비용과 대응

| 비용 | 대응 |
|---|---|
| 체크포인트에 대화가 평문으로 남는다 (S03) | 체크포인트 저장을 암호화한다. 방법은 구현 시점의 공식 문서로 확인한다 |
| 의존성과 버전 변화 | 버전을 고정하고 `requirements.lock`에 반영한다 |

| 응답 지연이 늘 수 있다 | 이식 전후 M11을 비교한다 |

## 다시 검토하는 조건

- 이식 후 한 턴 응답 시간이 눈에 띄게 늘어난다.
- 사용자 확인과 검증 후 재작성을 넣었는데 M1이 줄지 않는다. 이 경우 LangGraph를 고른 이유의 절반이 사라진다.
- 체크포인트 암호화가 현실적으로 어렵다.
