# 사례 정리: 문제 숫자 → 원인 → 조치 → 결과 숫자

바로의 AI 품질을 재고 고친 과정을 문제별로 정리한다. 숫자의 출처는 모두 `eval/results/`의 결과 문서이고, 문제마다 해당 문서를 적었다. 진행 상황은 `roadmap.md`, 지표의 정의는 `metrics.md`에 있다.

## 한눈에 보기

| 문제 | 처음 | 지금 | 잰 곳 |
|---|---|---|---|
| 한 턴 응답 시간 (중앙값) | 37.1초 | 11.4~12.6초 | 개발 세트 |
| 초안의 지어낸 사실 | 초안 33건 중 32~33건에 있음 | 10건 중 0~1건, 보류 세트 13건 중 0건 | 아래 "비교할 때 주의" 참고 |
| LLM 요청에 실린 식별정보 원문 | 384건 | 0건 | 개발 세트, 보류 세트 |
| 미지원 죄목을 지원하는 것처럼 처리 | 100% | 0% | 개발 5건, 보류 2건 |
| 판례의 주된 죄명이 사건과 맞음 | 23.8% | 71.9% | 지원 죄목 33건 |
| 답한 항목을 다시 물음 | 16회 | 5회 | 개발 10건, 같은 조건 |
| LLM 실패를 정상처럼 돌려줌 | 12개 조합 중 2개 | 0개 | 가상 사례 1건 |

**비교할 때 주의.** 처음과 지금 사이에 서비스 모델(`gpt-5-mini` → `gpt-6.1-terra`), 판정 모델(`gpt-5` → `gpt-6.1-sol`), 판정 기준(2판 → 3판)이 모두 바뀌었다. 지어낸 사실의 처음과 지금은 같은 자로 잰 숫자가 아니다. 단계마다 같은 조건으로 잰 전후는 아래 각 절에 있다.

## 어떻게 쟀는가

- **평가 사례 53건.** 모두 가상의 사건이다. 사례마다 처음 서술과, 필수 정보 12개 각각에 대해 "처음 서술에 있었는지"와 "물으면 돌려줄 답"을 적어 두었다. 정답은 해시로 잠가 CI가 검사한다.
- **모의 사용자가 대화한다.** 평가기가 서비스에 사건을 보내고, 서비스가 물으면 정답에서 답을 꺼내 돌려준다. 정답에 "모른다"고 적힌 항목은 모른다고 답한다. 초안이 나올 때까지 진행한다.
- **규칙 검사와 LLM 판정을 함께 쓴다.** 질문 수, 다시 물은 횟수, 식별정보는 규칙으로 센다. 초안의 지어낸 사실과 단정 표현은 판정 모델이 대화 기록과 초안을 대조해 찾는다.
- **개발 세트 38건과 보류 세트 15건.** 지시문은 개발 세트를 보면서 고쳤다. 보류 세트는 한 번도 열지 않고 두었다가 마지막에 한 번 쟀다.
- **부분 세트 10건.** 개선 하나의 효과는 개발 세트 10건으로 쟀다. 전체 1회가 약 5달러였기 때문이다.
- **한 번에 한 가지.** 구조 변경과 동작 변경을 한 PR에 섞지 않았고, 동작을 바꾸는 PR에는 전후 숫자를 적었다.

## 1. 응답이 느리고 비쌌다

**문제.** 기준선에서 한 턴 응답의 중앙값이 37.1초였다. 사용자는 질문 하나에 답할 때마다 그만큼 기다렸다. 서비스 비용의 90%가 정보 추출 호출이었다 (`baseline-1.md`).

**원인.** 정보 추출은 매 턴 대화 전체를 다시 읽고 항목 12개를 판정한다. 이 호출이 모델의 기본 추론 강도로 돌고 있었고, 출력의 대부분이 추론 토큰이었다.

**조치와 결과.** 추론 강도를 `low`로 낮췄다 (`extract-low-dev10.md`, 같은 10건).

| | 이전 | 이후 |
|---|---|---|
| 한 턴 응답 중앙값 | 38.0초 | 16.4초 |
| 정보 추출 비용 | 0.894달러 | 0.397달러 |
| 추론 토큰 | 318,592 | 73,856 |
| 첫 턴 재현율 / 정밀도 | 90.0% / 51.9% | 96.7% / 52.7% |

품질이 나빠진 근거는 없었다. 이 작업을 가장 먼저 한 이유는 이후의 모든 측정이 이 호출을 거치기 때문이다. 먼저 줄이면 그 뒤의 평가가 모두 싸지고 빨라진다.

**한계.** 매 턴 전체를 다시 추출하는 구조는 그대로다.

## 2. 초안에 사용자가 말하지 않은 사실이 들어갔다

고소장은 수사기관에 내는 문서다. 사용자가 말하지 않은 사실이 들어가면 사용자가 그 내용에 책임을 지게 된다. 이 서비스에서 가장 중요하게 본 문제다.

**문제.** 기준선에서 초안 33건 가운데 32건(판정 기준을 고친 뒤에는 33건)에 지어낸 사실이 있었다 (`baseline-1.md`, `baseline-1-judge-v2.md`).

**원인을 먼저 찾았다.** 고치기 전에 지어낸 사실 49개를 하나씩 읽고 어느 단계에서 생겼는지 나눴다 (`m1-origin-dev10.md`).

| 생긴 곳 | 개수 |
|---|---|
| 초안 작성: 범죄 요건과 경위를 채우려고 더한 서술 | 24 |
| 초안 작성: 감정과 피해의 정도 ("정신적 고통", "피해가 극심") | 12 |
| 정보 추출 결과에 이미 있던 내용 | 9 |
| 추출 요약의 "제공되지 않았다"를 초안이 "없다"로 단정 | 4 |

73%가 초안 작성 단계에서 새로 생겼다. 이 분석으로 계획이 바뀌었다. 원래는 추출 결과를 사용자에게 보여 주고 확인받으려 했는데, 그 방식이 닿을 수 있는 것은 27%뿐이었다. 그래서 확인 대상을 "초안에서 대화에 근거가 없는 문장"으로 바꿨다.

**조치와 결과.** 단계를 나눠 넣고 각각 쟀다 (같은 추출 결과에서 초안만 다시 써서 비교, 개발 10건, 판정 2판).

| 단계 | 지어낸 사실 | 지어낸 사실이 있는 초안 | 문서 |
|---|---|---|---|
| 처음 | 49 | 10/10 | |
| 작성 지시문 수정 | 21 | 8/10 | `compose-prompt-dev10.md` |
| + 초안 검증 후 재작성 | 7 | 4/10 | `prompt-verify-dev10.md` |

- **작성 지시문.** 지어내게 만드는 지시를 찾아 고쳤다. 예: 처벌 요구 문장의 예시에 "피해가 극심하므로"가 들어 있어 모델이 그대로 따라 썼다. "기망, 착오, 처분행위, 손해를 한 번씩 쓰라"는 지시는 단계를 채우려고 사실을 더하게 했다.
- **검증 후 재작성.** 쓴 초안을 대화와 대조해 근거 없는 표현을 찾고 그 표현만 고친다.
- **사용자 확인.** 검증이 찾은 표현을 바로 지우지 않고 사용자에게 "사실이 맞나요?"라고 묻는다. 맞다고 답한 표현은 남기고 아니라고 답한 표현만 고친다 (`confirm-dev10.md`: 물은 14개 중 9개가 남고 5개를 고침).

**날짜가 다른 일에 붙는 문제.** 모델을 옮긴 뒤 남은 지어낸 사실은 한 종류였다. 사용자는 "보증금을 보낸 날"만 말했는데 초안이 그 날짜를 "집주인이라고 소개하고 서류를 보여 준 날"에도 붙였다. 세 곳을 고쳤다.

1. 작성 지시문: 날짜는 데이터가 밝힌 일에만 붙인다 (`draft-date-dev10.md`).
2. 정보 추출: 원인은 그 앞 단계에 있었다. 작성 요청에 실리는 날짜 요약이 "2026년 5월 12일이라는 날짜가 확인됩니다"처럼 날짜만 담고 있어, 작성 모델은 규칙을 받아도 어디에 붙일지 알 수 없었다. 요약에 무슨 일의 날짜인지를 함께 적게 했다 (`extract-date-of-what-dev10.md`).
3. 초안 검증: 날짜가 다른 일에 붙었는지를 대조하고, 그런 표현은 사용자에게 묻지 않고 날짜만 뗀다. "이 일이 사실인가요?"라고 물으면 그 일은 있었으니 맞다고 답하게 되고 날짜가 그대로 남기 때문이다. 날짜를 뗀 문장은 미리보기에서 사용자에게 알린다 (`verify-date-dev10.md`).

**지금.** 같은 10건을 4회 실행해 0·0·1·0건, 보류 세트 13건에서 0건이다 (`wobble-dev10.md`, `holdout-final-summary.md`). 보류 세트의 한 사례에서 계약일이 이체에 붙었고 검증이 잡아 날짜만 뗐다.

**한계.**
- 판정은 정확하지 않다 (다음 절). 0건은 "판정이 찾지 못했다"는 뜻이다.
- 초안이 사용자가 말한 사실을 빠뜨렸는지는 재지 않는다. 지어내지 않게 하려고 덜 쓰게 만든 것일 수 있다. 모델을 옮긴 뒤 초안이 3분의 1쯤 짧아졌다.
- 검증은 날짜 문제를 매번 잡지는 못한다. 한 사례를 세 번 중 한 번 놓쳤다.

## 3. 채점 결과를 믿을 수 있는가

지어낸 사실은 판정 모델이 센다. 그 숫자를 근거로 고치려면 판정이 얼마나 맞는지 알아야 했다.

**확인한 것.**

- **기준선의 판정을 사람이 검수했다.** 판정이 잡은 항목을 읽고 판정 기준을 고쳤고, 기준을 만들 때 쓰지 않은 새 표본 16개로 확인했다 (16/16).
- **같은 초안을 다시 판정하면 숫자가 달라진다.** 옛 판정 모델은 같은 초안 10건에서 21건과 16건을 냈고, 지적이 서로 일치한 비율은 43%였다. 새 판정 모델은 13건과 12건, 87%였다 (`judge-model-dev10.md`).
- **두 판정이 낸 지적 25개를 사람이 검수했다.** 맞는 지적 13개, 지어낸 사실이 아닌 것 12개였다. 판정 기준 3판은 맞는 13개 중 9개를 짚고, 아닌 12개 중 5개를 잘못 짚는다. 2판은 6개와 8개다.

**결론.** 어느 판정도 정확하지 않다. 그래서 지어낸 사실의 건수는 대략의 크기로 읽고, 판정 모델이나 판정 기준이 다른 숫자는 서로 비교하지 않는다. 결과 문서마다 판정 모델과 기준 판본을 적어 둔다.

**실행 간 흔들림.** 같은 코드로 같은 10건을 되풀이하면 물은 항목 수는 58~62개, 다시 물은 횟수는 6~9회, 질문 수 평균은 10.7~11.7개 사이에서 움직인다 (`wobble-dev10.md`). 이보다 작은 차이는 1회 측정으로 가르지 않는다. 앞서 1회씩 비교한 결과 가운데 이 폭 안에 드는 것은 차이로 보지 않는다고 해당 문서에 적었다.

## 4. 이미 답한 것을 다시 물었다

**문제.** 사용자가 답했는데 같은 질문이 다시 나왔다. "왜 그 말을 믿었나요?"에 "신분증 사본과 등기권리증을 보여 줬습니다"라고 답해도 "믿은 이유가 언급되지 않았습니다"라며 다시 물었다. "모르겠어요"라고 답한 항목도 다시 물었다.

**첫 수정과 되돌림.** 같은 항목을 한 번만 묻게 했다. 다시 물은 횟수는 20 → 0이 됐다 (`ask-once-dev10.md`). 그런데 사용자가 일부만 답했거나 엉뚱하게 답한 경우에도 다시 묻지 않으므로 정보를 잃는다. 그 손실을 잴 방법이 없는 채로 기본값을 바꾼 것이어서 되돌렸다.

**원인.** 횟수의 문제가 아니었다. 정보 추출은 사용자의 말만 이어 붙여 받아서 어떤 말이 어느 질문의 답인지 몰랐다. 그리고 매 턴 전체를 다시 판정해서 이미 답한 항목이 "없음"으로 돌아가곤 했다.

**조치.**
1. 방금 한 질문과 그 답을 짝지어 추출에 알려 준다.
2. 답했거나 모른다고 한 항목은 고정한다. 모른다고 한 항목을 사용자가 나중에 말하면 풀린다.
3. 두 번째로 물을 때는 빠진 것만 묻고, 세 번째는 없다.

**손실을 잴 수 있게 했다.** 평가에 엉뚱하게 답하는 모의 사용자를 넣었다. 세 번에 한 번은 질문과 상관없는 말을 하고, 서비스가 다시 물으면 그때 정답을 준다. 다시 물어 정답을 받았으면 "되찾음"이다.

| 같은 조건 (개발 10건, 각 1회) | 이전 | 이후 |
|---|---|---|
| 답한 항목을 다시 물은 횟수 | 16 | 5 |
| 엉뚱한 답을 되찾은 수 | 17/18 | 16/17 |
| 질문 수 평균 | 13.7 | 12.8 |

다시 묻는 일은 줄고, 필요한 되묻기는 그대로 남았다 (`answer-aware-dev10.md`).

**한계.** 세 가지 변경을 함께 넣어 각각의 효과를 따로 재지 않았다. 구성마다 한 번 잰 것이다.

## 5. 식별정보가 원문 그대로 외부 모델로 나갔다

**문제.** 기준선의 LLM 요청에 이름, 전화번호, 계좌번호, 주소 원문이 384건 실려 있었다.

**조치.** AI 서비스 입구에서 식별정보를 `[이름1]`, `[계좌번호1]` 같은 표식으로 바꾸고, 응답에서 되돌린다. 입력 화면에서 받은 이름·주소·전화번호와 전화·계좌 정규식을 쓴다.

**결과.** 요청 속 식별정보 122 → 0건 (같은 10건, `pii-mask-dev10.md`). 그 뒤의 모든 실행과 보류 세트에서 0건이다.

**대가.** 첫 턴 재현율이 100% → 90%로 내려갔다. 놓친 3개 중 2개가 표식으로 바뀐 자리였다. 모델이 표식을 "값이 있는 것"으로 읽지 못한 것으로 보인다. 지시문에 표식을 값으로 읽으라는 안내를 넣었으나 그 효과만 따로 재지는 않았다.

**한계.** 입력 화면에 없는 이름(제3자, 닉네임, 상호)은 가리지 못하고, 이 지표도 그것을 세지 못한다.

## 6. 지원하지 않는 죄목을 지원하는 것처럼 처리했다

**문제.** 서비스가 제대로 다루는 죄목은 사기다. 그런데 명예훼손이나 횡령 사건을 넣어도 사기 양식으로 대화를 진행하고 초안을 썼다. 미지원 사례 5건 모두 그랬다 (100%).

**조치.** AI 서비스는 미지원 죄목이면 세션을 만들지 않고 미지원으로 답한다. 서버는 아무것도 저장하지 않고 안내한다. 화면은 지원 죄목만 고를 수 있게 하고 나머지는 "준비 중"으로 막는다.

**결과.** 100% → 0% (개발 5건). 보류 세트의 2건도 미지원으로 처리됐다.

범위를 넓히는 대신 좁혀서 정확하게 하는 쪽을 택했다 (`decisions/0001-scope.md`).

## 7. 보여 주는 판례가 사건과 맞지 않았다

**문제.** 사기 사건에 보여 준 판례 가운데 주된 죄명이 사기인 것이 23.8%였다.

**원인.** 판례의 죄명 라벨을 글자로 걸렀다. 라벨에 "사기"라는 글자가 있으면 통과시켜서 "군사기밀보호법위반"도 통과했다. 그리고 "사기"가 든 판례 1,329건 가운데 죄명이 하나뿐인 것은 313건이었다. 나머지는 마약, 교통사고 같은 다른 죄명과 함께 붙어 있었고, 서술과 가까운 순서로만 고르면 이런 판례가 앞에 왔다.

**조치.** 죄명 단위로 비교하고, 찾는 죄목만 다룬 판례를 먼저 고른다.

**결과.** 23.8% → 67.7% (`rag-primary-dev33.md`), 모델을 옮긴 뒤 71.9% (`rag-model-dev33.md`).

**한계.** 죄명이 맞는지만 잰다. 사실관계가 비슷한지는 재지 않는다.

## 8. LLM 호출이 실패해도 정상처럼 보였다

**문제.** 초안 작성 호출이 실패하면 빈 문자열을 돌려주고 정상 응답처럼 진행했다. 판례 요약이 실패하면 원문 앞부분을 요약처럼 보여 주고, 그 결과를 7일 동안 캐시했다.

**조치.** 실패는 오류로 올리고 사용자에게 알린다. 작성 실패는 502로 답하고 화면이 다시 시도하게 한다. 요약하지 못한 판례는 "요약하지 못해 원문 앞부분을 보여 준다"고 표시하고 캐시하지 않는다.

**측정.** 호출 종류 하나에만 실패를 주입하고 응답이 그 실패를 드러내는지 봤다 (호출 6종 × 실패 방식 2종, `failure-injection.md`). 첫 측정에서 은폐 2건이 나왔다. 모델이 "죄송합니다. 지금은 답변할 수 없습니다."를 돌려주면 그 문장을 판례 키워드로 썼고, 고소이유가 빈 초안을 완성본으로 돌려줬다. 둘을 고친 뒤 0건이다.

**한계.** 가상 사례 1건, 조합당 1회다. 재작성 호출의 형식 오류는 그 호출이 일어나지 않아 재지 못했다.

## 9. 쓰던 모델이 종료된다

**문제.** 서비스 모델 `gpt-5-mini`와 판정 모델 `gpt-5`가 2026-12-11에 종료된다는 것을 작업 중에 확인했다.

**조치.** 호출 종류별로 나눠 옮겼다. 호출 계층을 하나로 모아 두었기 때문에 작업별 모델을 설정으로 바꿔 가며 잴 수 있었다.

| 호출 | 잰 것 | 결과 | 문서 |
|---|---|---|---|
| 정보 추출 | 물어야 할 85개 중 물은 수 | 옛 모델 43~46, `gpt-6-luna` 49~55, `gpt-6.1-terra` 60 | `extract-model-dev10.md` |
| 판정 | 같은 초안을 두 번 판정했을 때의 일치 | 옛 모델 43%, `gpt-6.1-sol` 87% | `judge-model-dev10.md` |
| 작성·검증 | 지어낸 사실 (판정 3판) | 옛 모델 6건, 새 모델 2~3건. 작성·검증 65초 → 14초 | `service-model-dev10.md` |
| 판례 키워드·요약 | 키워드가 정답과 맞음 | 30/33 → 33/33 | `rag-model-dev33.md` |

모든 호출을 `gpt-6.1-terra`로 정했다. 더 싼 `gpt-6-luna`는 고소장 한 건이 약 0.017달러로 5분의 1이지만 물어야 할 것을 덜 물었다. 고소장 한 건의 비용은 약 0.085달러다.

판정 모델은 옛 모델이 살아 있는 동안에만 옛 판정과 새 판정을 같은 초안으로 견줄 수 있어서 먼저 옮겼다.

## 시도했지만 넣지 않은 것

| 시도 | 결과 | 처리 |
|---|---|---|
| 추출 입력에 AI의 질문을 함께 넣기 | 효과를 확인하지 못함 (`extract-dialogue-dev10.md`) | 넣지 않음 |
| 같은 항목을 한 번만 묻기 | 다시 물음 20 → 0. 정보를 잃는 손실을 재지 못함 | 기본값에서 뺌 |
| 정보 추출만 더 싼 모델로 | 비용 5분의 1. 물어야 할 것을 덜 물음 | 택하지 않음 |
| 추출 결과를 사용자에게 확인받기 | 지어낸 사실의 27%에만 닿음 | 초안의 문장을 확인받는 방식으로 바꿈 |
| 다른 공급자의 모델과 비교 | 하지 않음. 호출 계층은 공급자를 더할 수 있게 돼 있다 | 범위 밖 |

## 보류 세트 최종 측정

지시문을 고치는 동안 열지 않은 15건을 마지막에 한 번 쟀다 (`holdout-final-summary.md`).

| 지표 | 보류 세트 (13건, 1회) | 개발 세트 (10건, 4회의 폭) |
|---|---|---|
| 지어낸 사실 | 0건 | 0~1건 |
| 물어야 할 항목 중 물은 비율 | 74.8% | 68.2~72.9% |
| 다시 물은 횟수 (한 건당) | 1.0 | 0.6~0.9 |
| 식별정보 | 0건 | 0건 |
| 완료율 | 100% | 100% |

보지 않은 사례에서도 같은 범위였다. 다만 고치기 전 코드로 보류 세트를 잰 적이 없어 전후 비교는 아니다. 개선의 크기는 개발 세트의 전후 숫자로 말하고, 이 결과는 그 숫자가 개발 세트에만 맞춘 것이 아니라는 확인이다.

## 남은 문제

- **빠뜨린 사실을 재지 않는다.** 초안이 사용자가 말한 사실을 얼마나 담았는지의 지표가 없다.
- **판정이 정확하지 않다.** 지어낸 사실의 건수는 대략의 크기다.
- **모의 사용자의 답이다.** 실제 사용자는 더 흐리게, 더 길게, 질문과 다르게 답한다. 실제 사람이 써 본 결과는 없다.
- **대부분 10건, 1~4회로 쟀다.** 개발 세트 전체(38건)를 옮긴 모델로 다시 재지 않았다.
- **물어야 할 항목의 4분의 1은 묻지 않고 넘어간다.** 85개 중 23~27개다.
- **식별정보 가리기는 입력 화면에 없는 이름을 놓친다.**
- **사실관계가 비슷한 판례인지는 재지 않는다.**
