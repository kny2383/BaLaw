# 로드맵

바로 리팩토링의 할 일과 진행 상황이다.

- 상태: ✅ 완료 (PR 병합) · 🟡 진행 중 · ⬜ 시작 전
- **완료 기준**: PR이 병합되고, 동작을 바꾼 항목은 평가기로 전후 숫자를 `eval/results/`에 남겼을 때 완료로 본다.
- 단계 번호(0~7)는 변경의 종류다. 실제로 하는 순서는 아래 "진행 순서"를 따른다.
- 구조 변경과 동작 변경은 한 PR에 섞지 않는다.
- 항목 ID는 `gap-analysis.md`(F·S·Q), 지표는 `metrics.md`(M1~M12)를 따른다.

## 진행 순서

1. **정보 추출 호출 개선** (5단계 중 먼저). 서비스 비용의 90%와 응답 시간 대부분이 이 호출이다. 먼저 고치면 이후 모든 평가가 싸지고, 구조 변경의 동일성 확인도 빨라진다.
2. **흔들림 측정과 AI API 동작 테스트** (2·3단계 남은 것). 구조 변경 전 안전망이다.
3. **LangGraph 이식** (4단계). 현재 흐름만 그대로 옮기고 숫자가 같은 범위인지 확인한다 (결정 0003).
4. **나머지 품질 개선** (5단계). 사용자 확인, 검증 후 재작성, 판례 검색, 식별정보 치환, 실패 처리.
5. **횡령 확장** (6단계), **사용성 테스트와 보류 세트 최종 측정** (7단계).

비용이 거의 들지 않는 일은 순서와 관계없이 틈틈이 한다: 모욕 재결정, 횡령 요구사항 정의서, M10 실패 주입 측정.

## 평가 예산 규칙

- 전체 개발 세트(38건)로 재는 것은 정보 추출 개선 전후, LangGraph 이식 전후, 마지막 최종 측정뿐이다.
- 그 밖의 개선은 10건 부분 세트(`--only`)로 재고, 결과 문서에 "부분 세트"라고 적는다.
- 실행 전에 예상 비용을 적고 승인을 받는다. 2026-11-26 기준 전체 1회는 약 5달러(서비스 3.2 + 판정 1.8)이고, 정보 추출 개선 뒤 다시 추정한다.
- 보류 세트(15건)는 마지막에 한 번만 연다.

## 4. 구조 변경 🟡

동작은 바꾸지 않는다. 바꾼 뒤 평가기를 돌려 이식 전과 같은 범위의 숫자가 나오는지로 확인한다.

| 항목 | 상태 | 비고 |
|---|---|---|
| LangGraph로 현재 흐름 이식: 추출 → 질문 선택 → 작성 | 🟡 | 결정 0003. 분류·사용자 확인은 넣지 않는다. 흐름 이식은 끝났고(`ai/flow/`, 메모리 체크포인터), 평가기로 하는 동일성 확인이 남았다 |
| 대화 상태를 PostgreSQL 체크포인트로 (F21, 복원 때 LLM 재실행 제거) | 🟡 | `ai/flow/checkpoint.py`. 서버는 고소장을 지울 때(사용자 삭제, 다운로드 1일 뒤 자동 삭제) AI 세션을 먼저 지운다. 남은 것: 평가기로 하는 동일성 확인 |
| 체크포인트와 채팅 기록 암호화 (S03) | ✅ | 체크포인트: AES로 암호화하고, 실제 DB를 훑어 평문이 없는지 검사하는 테스트를 둔다. 서버의 채팅 기록: 내용과 이유 열을 Fernet으로 암호화하고, 이미 저장된 행은 마이그레이션이 암호화한다. 암호화하지 않은 채 남은 것: 고소장의 판례 검색 결과(`rag_keyword`, `rag_cases`) |
| LLM 호출을 한 계층으로 (LangChain 모델 인터페이스 + 작업별 모델 설정) | ⬜ | 결정 0002, 0003 |
| 서버의 불필요한 OpenAI 키 요구 제거, `RAG_ENABLED`·`python-multipart`·서버 이미지 컴파일러 정리 | ⬜ | |

## 5. 품질 개선 🟡

| 항목 | 상태 | 지표 |

| **정보 추출 호출 개선** (가장 먼저): 추론 강도 설정(완료, `eval/results/extract-low-dev10.md`), 추출 입력에 AI 질문 포함(측정했으나 효과를 확인하지 못해 반영하지 않음, `eval/results/extract-dialogue-dev10.md`), 매 턴 전체 재추출 줄이기. 추출 입력이 최근 1,800자만 담아 긴 서술이 통째로 빠지던 문제는 고쳤다 (처음 서술을 지키고 상한 6,000자) | 🟡 | M1, M2, M11, M12 |

| 호출마다 프롬프트 판본·모델·토큰·비용·지연 기록 (기존 관측 도구 연결 검토) | ⬜ | M11 |
| 지어낸 사실이 생기는 단계 분석 | ✅ | M1. 49개 중 36개(73%)가 작성 단계에서 생긴다. `eval/results/m1-origin-dev10.md` |
| 초안 검증 후 재작성 (대화에 근거 없는 문장을 찾아 빼고 다시 쓴다) | 🟡 | M1 21 → 7 (개발 10건, 1회, 일부는 판정 흔들림). `eval/results/prompt-verify-dev10.md`. 남은 확인: 판정 흔들림의 폭, 보류 세트 |
| 작성 전 사용자 확인 (interrupt): 검증이 찾은 문장을 사용자에게 확인받는다. 추출 결과를 확인받는 방식은 닿는 범위가 27%라 택하지 않았다. AI 서비스의 확인 단계와 재개 엔드포인트는 들어갔고(`DRAFT_CONFIRM`), 개발 10건을 판정 없이 돌려 물은 14개 중 9개가 남고 5개를 고쳤다(`eval/results/confirm-dev10.md`). 서버는 확인을 기다리는 초안을 저장하지 않고 답을 받는 엔드포인트(`/generate/confirm`)를 둔다. 화면은 확인이 필요하면 미리보기 전에 표현과 이유를 보여 주고 답을 받는다. 브라우저에서 가상 사건 한 건으로 확인 창 → 답 → 고쳐 쓴 초안의 미리보기까지 이어지는 것을 확인했다. 검증이 구절만 인용하게 하고 화면이 문장 안의 구절을 강조한다(`eval/results/confirm-phrase-dev10.md`). 기본으로 켰다. 남은 것: 확인을 켠 상태의 M1, 실제 사용자의 답이 모의 사용자와 얼마나 다른지 | 🟡 | M1 |
| 작성 프롬프트 점검: 감정·피해 정도 서술(지어낸 사실의 24%), 사기 구성요건 서술 강제, 추출 요약의 점검 메모 투 | 🟡 | M1 49 → 21 (같은 추출 결과, 개발 10건, 1회). `eval/results/compose-prompt-dev10.md`. 남은 확인: 작성 흔들림 대조(응답 시간·비용 증가의 원인 포함), 보류 세트 |
| 실패 처리: 재시도 후 명시적 오류, AI 오류 원문 노출 제거 | 🟡 | M10. 작성·재작성 호출의 실패를 빈 문자열로 돌려주던 것을 오류로 올린다 (작성 실패는 502, 재작성 실패는 `rewrite_failed`). 화면은 생성 실패를 알리고 다시 시도하게 한다. 서버는 실패 응답에 예외 원문을 넣지 않고 종류만 기록하며, 본문이 빈 초안을 완성본으로 저장하지 않는다. 남은 것: 판례 검색 쪽 호출, 실패 주입 측정 |
| S05 식별정보 치환 후 전송, 응답에서 복원 (입력 화면의 이름·주소 값과 전화·계좌 정규식) | 🟡 | M9. AI 서비스 입구에서 치환하고 응답에서 되돌린다 (`ai/services/pii.py`). 측정: M9 122 → 0, 첫 턴 재현율 100 → 90% (`eval/results/pii-mask-dev10.md`). 서버가 입력 화면의 이름·주소·전화번호를 넘겨준다. 남은 것: 입력 화면에 없는 이름(제3자, 닉네임), 추출 프롬프트가 표식을 값으로 읽게 하는 보완 |
| F11 미지원 죄목은 미지원으로 반환 | ⬜ | M5 |
