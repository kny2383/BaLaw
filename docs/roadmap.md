# 로드맵

바로 리팩토링의 할 일과 진행 상황이다.

- 상태: ✅ 완료 (PR 병합) · 🟡 진행 중 · ⬜ 시작 전
- **완료 기준**: PR이 병합되고, 동작을 바꾼 항목은 평가기로 전후 숫자를 `eval/results/`에 남겼을 때 완료로 본다.
- 단계 번호(0~7)는 변경의 종류다. 실제로 하는 순서는 아래 "진행 순서"를 따른다.
- 구조 변경과 동작 변경은 한 PR에 섞지 않는다.
- 항목 ID는 `gap-analysis.md`(F·S·Q), 지표는 `metrics.md`(M1~M12)를 따른다.

## 진행 순서

1. **정보 추출 호출 개선** (5단계 중 먼저). 서비스 비용의 90%와 응답 시간 대부분이 이 호출이다. 먼저 고치면 이후 모든 평가가 싸지고, 구조 변경의 동일성 확인도 빨라진다.
2. **흔들림 측정과 AI API 동작 테스트** (2·3단계 남은 것). 구조 변경 전 안전망이다.
3. **LangGraph 이식** (4단계). 현재 흐름만 그대로 옮기고 숫자가 같은 범위인지 확인한다 (결정 0003).
4. **나머지 품질 개선** (5단계). 사용자 확인, 검증 후 재작성, 판례 검색, 식별정보 치환, 실패 처리.
5. **사용성 테스트와 보류 세트 최종 측정** (7단계). 횡령 확장(6단계)은 하지 않는다 (결정 0001, 2026-11-27).

남은 작업은 위 순서대로 하고, 지금 범위에서 필요하지 않은 항목은 "하지 않음"으로 적고 넘어간다. 측정(흔들림, 보류 세트)은 코드 변경이 끝난 뒤 마지막 코드로 한 번에 한다.

### 모델 이전 (2026-11-27 추가)

서비스가 쓰는 `gpt-5-mini`와 평가 판정 모델 `gpt-5`가 **2026-12-11에 종료**된다 (OpenAI 지원 종료 문서, 2026-11-27 확인). 남은 순서를 아래로 바꾼다. 절차는 결정 0002의 "새 모델이 나왔을 때의 절차"를 따른다.

1. 준비: 평가기에 초안 작성 없이 대화만 재는 실행, 새 모델의 단가와 추론 강도 값.
2. 정보 추출 모델 정하기. 호출 수가 가장 많고(서비스 비용의 약 70%) 정답으로 잴 수 있어 먼저 한다.
3. 판정 모델을 새 모델로 바꾸고, 같은 초안을 옛 판정과 새 판정으로 비교해 숫자를 잇는다. 옛 판정 모델이 살아 있는 동안에만 할 수 있다.
4. 작성·검증·재작성 모델 정하기.
5. 옮긴 모델로 개발 세트의 새 기준을 잰다. 그 뒤에 흔들림과 보류 세트 최종 측정을 한다.

지금까지의 결과 문서(`eval/results/`)는 모두 `gpt-5-mini-2025-08-07`(서비스)과 `gpt-5-2025-08-07`(판정)로 잰 것이다. 옮긴 뒤의 숫자와 바로 비교하지 않는다.

## 평가 예산 규칙

- 전체 개발 세트(38건)로 재는 것은 정보 추출 개선 전후, LangGraph 이식 전후, 마지막 최종 측정뿐이다.
- 그 밖의 개선은 10건 부분 세트(`--only`)로 재고, 결과 문서에 "부분 세트"라고 적는다.
- 실행 전에 예상 비용을 적고 승인을 받는다. 2026-11-26 기준 전체 1회는 약 5달러(서비스 3.2 + 판정 1.8)이고, 정보 추출 개선 뒤 다시 추정한다.
- 보류 세트(15건)는 마지막에 한 번만 연다.

## 4. 구조 변경 🟡

동작은 바꾸지 않는다. 바꾼 뒤 평가기를 돌려 이식 전과 같은 범위의 숫자가 나오는지로 확인한다.

| 항목 | 상태 | 비고 |
|---|---|---|
| LangGraph로 현재 흐름 이식: 추출 → 질문 선택 → 작성 | 🟡 | 결정 0003. 분류·사용자 확인은 넣지 않는다. 흐름 이식은 끝났고(`ai/flow/`, 메모리 체크포인터), 평가기로 하는 동일성 확인이 남았다 |
| 대화 상태를 PostgreSQL 체크포인트로 (F21, 복원 때 LLM 재실행 제거) | 🟡 | `ai/flow/checkpoint.py`. 서버는 고소장을 지울 때(사용자 삭제, 다운로드 1일 뒤 자동 삭제) AI 세션을 먼저 지운다. 남은 것: 평가기로 하는 동일성 확인 |
| 체크포인트와 채팅 기록 암호화 (S03) | ✅ | 체크포인트: AES로 암호화하고, 실제 DB를 훑어 평문이 없는지 검사하는 테스트를 둔다. 서버의 채팅 기록: 내용과 이유 열을 Fernet으로 암호화하고, 이미 저장된 행은 마이그레이션이 암호화한다. 암호화하지 않은 채 남은 것: 고소장의 판례 검색 결과(`rag_keyword`, `rag_cases`) |
| LLM 호출을 한 계층으로 (LangChain 모델 인터페이스 + 작업별 모델 설정) | ✅ | 결정 0002, 0003. `ai/services/llm.py`. 호출 여섯 종류의 요청 본문이 바꾸기 전과 같은지를 테스트로 고정했다. 연결된 공급자는 OpenAI와 OpenAI 호환 서버다 |
| 새 모델의 단가와 추론 강도 값을 설정에 반영 | ✅ | `gpt-6-luna`, `gpt-6.1-terra`, `gpt-6.1-sol`의 단가를 넣었다. 평가 구성에서 `EVAL_LLM_MODEL_<작업>`으로 작업별 모델을 바꾼다. 새 모델은 추론 강도 `minimal`이 없고 `xhigh`·`max`가 있다. `none`은 `gpt-6-luna`와 `gpt-6.1-terra`에만 있고 `gpt-6.1-sol`은 `low`부터다. 세 모델 모두 실제 호출로 동작을 확인했다 (luna·terra는 정보 추출, sol은 판정). 날짜가 붙은 판본이 없어 별칭으로 쓴다 |

## 5. 품질 개선 🟡

항목마다 평가기로 전후 숫자를 남긴다. 판정은 판정 기준 3판으로 잰다 (2026-11-27부터. 그 전의 결과는 2판이라 M1을 바로 비교하지 않는다).

| 항목 | 상태 | 지표 |

| **정보 추출 호출 개선** (가장 먼저): 추론 강도 설정(완료, `eval/results/extract-low-dev10.md`), 추출 입력에 AI 질문 포함(측정했으나 효과를 확인하지 못해 반영하지 않음, `eval/results/extract-dialogue-dev10.md`), 매 턴 전체 재추출 줄이기(하지 않음). 되묻기: 같은 필수 항목을 한 번만 묻는 규칙을 넣었다가 기본값에서 뺐다. 다시 물은 횟수는 20 → 0이 됐지만, 일부만 답한 정보를 잃는 손실을 재지 못했다 (`eval/results/ask-once-dev10.md`). 그 뒤 답이 질문에 대한 답이 됐는지를 보고 정하게 고쳤다: 방금 한 질문과 답을 짝지어 추출에 알려 주고, 답했거나 모른다고 한 항목은 고정하고, 두 번째 질문은 빠진 것만 묻는다. 엉뚱하게 답하는 모의 사용자를 넣어 같은 조건으로 쟀다 (각 1회): 되묻기 16 → 5. 엉뚱한 답을 되찾는 것은 18번 중 17번, 17번 중 16번으로 그대로다. 같은 실행에서 넘어간 필수 항목은 24 → 26, 정답에 없는 항목을 물은 수는 39 → 43이었다. 구성마다 한 번 잰 것이라 이 차이들이 변화인지는 말할 수 없고, 세 가지 변경을 함께 넣어 따로 재지 않았다 (`eval/results/answer-aware-dev10.md`). 추출 입력이 최근 1,800자만 담아 긴 서술이 통째로 빠지던 문제는 고쳤다 (처음 서술을 지키고 상한 6,000자) | 🟡 | M1, M2, M11, M12 |

## 6. 기능 확장 (하지 않음)

죄목을 늘리지 않기로 했다 (결정 0001, 2026-11-27). 한 죄목에서 지어낸 사실·식별정보·실패 처리의 숫자를 끝까지 재는 쪽에 시간을 쓴다. 횡령 요구사항 정의서, 횡령 질문 정의, 증거 캡처 첨부 검토는 하지 않는다. 평가 세트의 횡령 사례는 미지원 죄목 처리(M5)를 재는 데 그대로 쓴다.
